# aigameengine: the plan (2026-11-02)

*Written after a day of questions, measurements on the real Pi and tube, and seven tracks of research. Updated 11-03. This doc is the queue. Evidence: a research report (citations, conflicts, what is unmeasured) and the 11-02 measurements on the Pi, summarized below.*

> The aim (09-30): a cross-platform, AI-first game engine that runs on a Raspberry Pi 4 as both the dev console and the target console, takes its inspiration from N64 recompilation techniques, and makes games that run without a dropped frame and scale from the weakest hardware to the most powerful gaming computer.
>
> The horizon (11-02): an engine meant to be used for a long time.

## Where it stands, in one page

*(Updated 11-08.)* **All 29 steps of [the queue](#the-queue) are built and ticked (11-05),** so every phase has its pieces in the tree: the tick contract and the receipt (Phases 0 and 1), the zombie game on Vulkan (2), `engine.h` as the boundary and the engine cut away from its games (3), any TV (4), the dev console (5), the kinds of game, each proven by one small game (6), the PC picture, with `gfx_soft.c` drawing the same frame with no driver at all (7), and the licence, packaging and online play (8). What isn't done is each gate's half on real hardware, waiting for compatibility's and performance's turns: nothing built since 11-04 has run on a real Pi (the ARM builds ran under qemu), no card from the image builder has been booted, no two real machines have played each other, and the Vulkan build hasn't been run on Linux since step 18. Each step's **Not built** line says the rest.

Since the queue, the engine has grown where Bike Lane Bash and REVA needed it, each recorded in the decisions table below or in `.claude/rules/engine.md`. For the game's first slice (11-05): a curb, liquid in a cup, a sound's pitch, and the walking map paced by its work. Then (11-06) came a desk text size and a game's own clips, including clips meant to be low. Also 11-06: REVA's hair simulated lock by lock as real hairs, and the engine's first GPU compute to run it (`engine/strands.inc`, `shaders/strand*.comp`), and the engine on an Android phone (`reva_native/android/`). On 11-07, the status line, from running a big game on the Pi.

[The review of 11-04](#review-11-04) is the snapshot from halfway through the queue: the gaps found on the way, the questions they raised, and how each was decided.

The engine first (11-03): gaps in the engine are the work, and the games are secondary to building it.

On 11-02, the first day the engine ran on the Pi, the proof game, Reva vs Zombies, ran at 4.4 fps.

The Pi itself is not the problem. In a bare test its GPU drew **400 individually posed bodies of 800 triangles in 13.2 ms of a 16.68 ms field**. The zombie game was sending 9.5 million indices a frame, about 12 times what fits, and **one film-quality hero body (1.06 million triangles) was about 95% of that**. Swapping her for a street citizen took the game from 4.4 to about 30 fps in one boot.

So the engine's gaps became the work. From 11-02, performance on the Pi was not the goal yet: fleshing out the engine was, capabilities and features before optimizing for the Pi, which comes later. The order was: fix the tick contract, build one body path and the Vulkan renderer through the zombie game, then cut the engine away from its games around that working proof. After that came any TV, the Pi dev console, the other kinds of game, and going public, with the PC's graphics list running alongside them. All of it is built now, and the order of what's left stands: features first, then compatibility, then performance.

## Is low level more efficient?

The conclusion is right, and the reason needs one correction. C with no script language is the right call: an interpreter would turn 1 ms of game logic into about 70-80 ms, and a field is 16.68 ms. But this engine is already plain C with no script layer, and it ran the zombie game at 4.4 fps. Only 8% of its CPU time was the engine's own code. 83% was the driver, the kernel and copying, doing what the engine asked for. **Going lower gains almost nothing from here. Asking for less gains everything.** One film mesh on a game path did more damage than any language could.

The correction is that high-level layers aren't only for humans. The ones that make things comfortable can go, such as class hierarchies, script sugar and reflection. The ones that check code matter more with an AI writing it, because memory errors lead the measured defects in LLM-written C, and agents erode their own code over time. So we keep a small header, handles, assertions, sanitizers and replay tests, all in plain C.

## How it's designed

**The frame holds by budget and schedule, and never reacts to itself.** The loop is a fixed schedule per game and mode: flip, fixed wait, input, one tick, submit, flip. A late frame is a break in the flip sequence, not a low average. Quality settings are one text table chosen at setup and never moved by a timer. `REVA_TIER=auto` goes away.

**On the tube, a budget is three numbers: CPU, vertex work and pixel work.** Each has to fit in a field on its own, because they overlap across frames, and each gets a 13 ms ceiling for margin. The shader's strength is part of the budget, since it moves the pixel side further than anything else. Measured on the Pi 11-02, through the Vulkan direct path at 480i (ms):

| Line in the frame | Indices | Draws | CPU | Vertex | Pixel |
|---|---|---|---|---|---|
| Clear and empty frame | | | 0.23 | 0.04 | 0.87 |
| 100 citizens and a 20k-triangle hero | 320k | 101 | 1.74 | 1.66 | 2.66 |
| Street, ground, two HUD layers | 194k | 103 | 0.72 | 0.87 | 2.23 |
| **Proof frame A: budget shader** | **514k** | **204** | **2.69** | **2.57** | **5.76** |
| Add one shadow pass and a four-tap lookup | | +101 | +1.16 | +4.46 | +8.72 |
| **Proof frame B** | | | **3.85** | **7.03** | **14.48** |
| Add six lights per pixel | | | +0.43 | +0.01 | +11.69 |
| **Proof frame C** | | | **4.28** | **7.04** | **26.17** |

Live, proof frame A has no late frames and plenty of room. B has one late frame in 299 at 480i with the pixel side at its limit, and none at 240p. C doesn't fit at either. So the game budget starts at A with a little of B: a cheaper shadow than four taps on everything is where the leftover goes, tested when the renderer exists.

**One body path, budgeted at the cook.** Crowd slot, scene cast and set actor become three owners of state with one `bodyPose` and one `bodyDraw` (the plan in `engine_capabilities.md` section 21), built as fixed pools with generational handles and no ECS library. A cook step refuses a game pack over its budget, so a film mesh can't reach a game path by accident. Instancing with shared poses is the crowd setting for when counts go up.

**The simulation writes a packet and never reads the renderer back.** This is the N64 lesson in usable form: the game writes the frame as data, and something else draws it. The packet carries stable IDs, a reset flag and a camera-cut count, so we never need RT64's guesswork or Zelda64Recomp's 284 KB of tagging patches. A hash of the packet gives an AI a text diff before any pixel check.

**Sixty-hertz ticks everywhere, one at a time, identical on x86 and ARM.** Built in Phase 1: a frame that owes k ticks passes through the loop k times and draws only on the last, so the rules don't change with the frame rate. The rules for matching across machines are `-ffp-contract=off` on every build, our own sin, cos and atan2 (`club_math.c`), and hashing fields rather than struct bytes. `qsort` is only used where equal keys can't change a result. Windows x86 and the Pi now agree bit for bit. Interpolation runs only on displays faster than 60 Hz, so until then a 100 Hz PC monitor shows 60 new images a second.

**The display layer boots safe, follows the standards and asks the player.** The engine only emits a whitelist of the four standard composite modes, so it can't produce an out-of-range scan rate, the one kind of signal damage on record. A mode from another region runs only after a button press answers a voice prompt. First boot uses the regional interlaced mode. 240p is offered with a 15-second auto-revert. Recovery works with no picture at all: a button held at power-on, a file on the boot partition, voice prompts. The picture aspect comes from the standard (the 720 raster is 15:11, and its central 704 samples are 4:3), with safe boxes of 90% and 80% until the player adjusts them. Nothing is tuned to the test set, and a measurement from it is a check on the standard, never the design value. Tube tricks are optional art, never carrying play information, each with a plain fallback.

**Vulkan 1.3 on every machine, with our own thin layer in C.** Chosen 11-02. 1.3 is the floor because it's what the Pi's driver has, and nothing is made for the PC that the Pi can't play. Features above the floor are PC settings only.

Details of how it's built:
- **The tube:** render straight into scanout buffers imported as `dma-buf` images, and flip them ourselves through KMS, with no SDL or window system in the way. Tested 11-02 with the real frame at both modes. It costs a little less than `VK_KHR_display`'s swapchain, which also works and is the fallback.
- **The PC:** a Vulkan surface on SDL2's window. SDL also stays for audio and pads. FIFO ran unpaced in a window on the GTX 1070 (3,640 presents a second), so the PC renderer can't trust it to pace until that's understood.
- **The late-frame counter:** the Pi's driver has no present-timing extensions, so the swapchain can't report flip times. The direct path gets the kernel's own flip timestamps, the same as the GL road.
- **Shaders:** GLSL compiled to SPIR-V at build time and shipped that way, with no shader compiling while a game runs. Pipelines are all built at load, so nothing compiles mid-play.
- **No extra libraries:** C against the plain Vulkan headers. No Vulkan Memory Allocator (it's C++), since the fixed pools below do that job.
- **The old GL path is gone** (step 18, 11-04): film and the old game modes were ported, then its code came out of every file. Vulkan is the only picture, and the no-display build hashes the packet.
- ⛔ Vulkan alone changes nothing in the picture. The look comes from the graphics list in Phase 7, and the API only makes it reachable.

**Virgo teaches this renderer, but isn't this renderer.** Virgo is a separate Vulkan renderer for the N64's RDP (Rust on `ash`). It recreates one old machine exactly: its input is RDP commands, its fragment shader was 13,196 instructions on the Pi, and a drawing field took 65 ms there against our 16.68. It stays its own project, and we take from it: `V3DV_FACTS_20261022.txt` and the plan's rung 8 (what the driver has and doesn't, what V3D's compiler does to loops and `discard`), and the shape of a one-way command stream behind a small C header (`virgo_rdp.h`).

**Pin the driver.** Pin the Pi OS image and Mesa version per release, and log the driver version with every number. Vulkan 1.3 on the Pi needs Mesa 24.3 or later.

**One small header and two tables separate engine from game.** Quake II's shape: a function table each way and a version number. Add an append-only rule, an engine-owned loop, and a `draw` that takes `const void* state`, which enforces the packet rule in C. An AI working on a game needs one header and one game file, a better limit on context than any style rule.

**Fixed pools and arenas now, threads when a budget demands them.** 83% of the zombie game's CPU was driver, kernel and copying on one GL context, which more threads can't reach. Count bytes per category and refuse content past the ceiling. An `ARENA_DEBUG` build makes every push a real `malloc`, or arenas blind the sanitizers.

**Packs become chunked, compressed and scoped to one game.** The Pi and PC both advertise BC1 and BC3, so one compressed texture can serve both. The format grows by appending a directory and footer, so old bytes never move, and faces, morphs and clips become chunks a rebake can't lose. Each game's cook produces a manifest, and refuses missing files, surplus files and anything over budget.

**AI writes and proves mechanism, but doesn't grade itself or judge the look.** The gate has five layers: an exact sim hash; a structured render report; exact image baselines per configuration; an LLM reader given a blessed reference, run by a separate agent; and a person's eyes. LLM vision alone scores 43-45% on real glitch tests, so it's never the sole judge, and agents don't own their own baselines. Every bug gets a tape before its fix.

**Data, tests and a pinned floor are what outlast the code.** A written pack spec, golden packs, `-std=gnu17` on every build line, a `.gitattributes`, a dated toolchain copy, permissive terms when it goes public. Pi 4 production runs to at least January 2034, which is a natural horizon for the floor.

24. [x] Step 6: particles, decals, level of detail, water, foliage. With film's beams as real lights that cast and move per frame (11-04).
    Built 11-05. Seven settings in `gfxset.inc`: `particles softfx decals lod refract foliage beamlights`. At `pi` it's 512 particles, short detail and 15 in a hundred of a set's foliage, with the rest off; `film` has the three that read the scene off, as its other PC features are. The receipt is the same, its pixels too: a frame with nothing that reads the scene is drawn in one pass, as it always was.
    **One scene that shows everything (11-05, added while this was being built):** one scene that tests all of the engine's capabilities at once, for testing. `reva_native/scenes/everything.py` writes one set, a station a capability, and shoots a camera a station (`--shoot OUT.png`, `--only`, `--list`). Twelve stations so far: bodies, materials, fur, cloth and toon, lights, water, particles, the timeline, decals, foliage, and level of detail near and far. A station whose packs a machine hasn't got is left out and said. Each step from here adds its own.
    **Particles, one system** (`engine/particles.inc`). A kind says what an emitter makes: how many a second, how long each lives, how fast and how wide it's thrown, how it falls and how the air stops it, its size and colour at birth and at death, a round sprite or a streak along its own going, laid over the picture or added to it. Twelve kinds by name: smoke, fire, sparks, steam, dust, embers, fountain, snow, exhaust, pyro, fuse, rain. A game makes an emitter (`E->particleKind`, `E->emitter`, `emitterAt`, `emitterRate`, `emitterGone`, `emitterBurst`), a set says one (`emitter`), and a set's can ride a mover, which is film's ask: a rocket's exhaust, pyro jets, fuse sparks. One pool, the machine's budget, the oldest making way; their own dice; stepped by the tick or by film's exposure clock. The old burst of dots (`E->particles`) and film's cigarette smoke are untouched.
    **The scene, read mid-frame** (`gfx_vk.c`, `g_mid`). Where `softfx`, `decals` or `refract` is on and the picture has its HDR target, a frame that has something to read the scene is drawn in two halves: everything solid, then its depth and colour are copied aside (set 0's bindings 9 and 8), then what's laid over it. Three things read it. **Soft particles:** a soft kind fades out over its last 0.45 units before a surface, so smoke has no line where it cuts the floor. **Projected decals** (`engine/decals.inc`, `E->decalAt`, a set's `decal`): a mark is a box thrown at the world, and whatever of the scene lies in the box takes it, so a splat folds over a step and a scorch goes up a wall. Stains (a mark, a splat, a scorch, a wet patch, a crack) multiply what's under them, so they take its light and shadow exactly; paint (a stripe, a picture) is laid over and lit by the sun and the sky with the sun's shadow. **Water:** what's under it shows, slid by its ripples and taking the water's colour by how much water the eye looks through, with a broken line of foam where it's thin and no hard edge where it meets ground. The engine asks for all three the same way on every machine, so the packet doesn't change with the settings: where the scene isn't read a soft particle is a plain one, a decal is a flat dark mark across its box's middle, and water is the tinted sheet it was.
    **Level of detail.** A prop can have lighter copies beside it (`~lod1`, `~lod2`) and a far-off picture of itself on two crossed cards (`~far`), and a set draws whichever suits how big the prop is in the picture; its shadow comes from a lighter one sooner. A set actor's body has `~lod1` and `~lod2` the same way, on the same skeleton, drawn on the actor's own pose and wearing what the body wears. The prop or body itself is the top detail, so film's meshes are never thinned up close, and the machine's `lod` setting says how soon detail lets go (0 a Pi's, 4 holds twice as far). `skate_src/author/lod.py` makes them: vertices gathered into cells, a seam of the texture and a hard edge kept apart, the cell's size searched for until the share of triangles is met, and the far picture splatted from the prop's own colours. R.E.V.A. 902 goes from 102,614 triangles to 30,572 and 8,326 in 3 seconds. Copies are looked for when a pack is loaded, never mid-frame.
    **Foliage.** `grass` and `scatter` in a set put copies of a prop about a patch of ground, each its own turn and size from a seed, and they lean in the set's wind in waves that cross the field, with their feet where they're planted. They're instances like any prop: culled one by one, one call for every copy of a mesh, a lighter copy far off. `skate_src/author/foliage.py` makes grass, a bush and a tree by code, and `groundwork.py` a pond's bed, a rock and steps, so the engine has them with no bought content.
    **Film's beams are lights** (this step's line). Every beam of a set is also a spot from its near end, along it, as wide as it opens, in its colour, made each frame from the beams as they stand, so a beam the timeline sweeps is a light that sweeps. `beamlights` 1 lights, 2 casts; a set's `beamlight <scale>` says how strongly, 0 for beams that are only a glow.
    **Found on the way.** A glow pipeline listed after the post pass's wasn't made on a machine with no HDR target, so fire and sparks would have drawn nothing at `pi` and `low` (it was mine, from this step's first day, and is fixed). A decal's first frame took any two axes across its throw, and a picture on a wall came out on its side and mirrored. A stain's colour multiplies light, so the 0.3 grey I first gave a wet patch was black. A flat mound lying exactly in the floor fought it for every pixel along its edge. A quoted heredoc ate a backslash and wrote a broken line of C, as `CLAUDE.md` says it will.
    **Not built:** the crowd's bodies have no lighter copies (a set actor's do; the crowd shares poses by mesh, and a copy has other meshes); a body has no far picture; paint decals aren't lit by a set's lamps, only the sun and the sky; a decal's surface direction comes from the depth's slope, so it's wrong for a pixel or two at an edge; water reflects the sky and not the set (screen-space reflections weren't built at step 22 either); foliage doesn't bend round a body walking through it; particles don't collide with the world or light it; soft particles, projected decals and refraction need the HDR target, so `low` has none of them.
25. [x] Step 7: 100 and 144 Hz, resolution and widescreen, the flat-panel look, depth of field, motion blur and TAA, HDR output. With film's camera track with roll, and post per frame (11-04).
    Built 11-05. Nine settings in `gfxset.inc`: `dof mblur taa tube hdrout interp` and the picture's own `width height aspect`, with `fullscreen` read before there's a window. The receipt is the same, its pixels too: none of it runs on a plain frame, and the rules never see any of it.
    **The picture and the glass** (`gfx_vk.c`, `pictureSize`, `presentPass`). The picture is what the engine draws and everything works in; the glass is what the display shows. They were always the same thing. A setting can now make the picture its own size (`width`, `height`: drawn at that and shown at the panel's, which never changes the display's mode), its own shape (`aspect 4:3`: black either side on a wider glass) or a tube's, and one last pass puts the picture on the glass in its place. When they're the same none of that runs. A shot is of the glass, so it shows what a player sees.
    **The flat-panel look** (`tube 1|2`, `shaders/tube.frag`, `data/tube.txt`). The engine draws the tube's own picture, 640 x 480 or 640 x 240 shown 4:3 as the Pi's 240p is, and the presenter shows it as a set does: each line smoothed along itself, colour far more than brightness (composite video's bandwidths), the beam a soft stripe that's fatter where it's bright, so 480 lines overlap into a solid picture and 240 leave dark between them, the two fields of a 480-line picture, the mask's stripes or slots, the tube's own curve and a slight bulge. ⛔ **Its numbers are the NTSC standard's and a typical set's, in `data/tube.txt`. Nothing has been measured off a tube.** The plan's word was "measured": the model takes a measured set's numbers in that file, and the measuring waits for the Pi's turn and the webcam.
    **100 and 144 Hz** (`interp`, `gfx_packet.c` `mixBuild`, `engine/clock.inc`). The rules still tick 60 times a second, one whole tick at a time. On a display faster than that, a refresh with no tick in it no longer sleeps: the renderer draws the picture that lies between the last two ticks' packets, pairing each draw with itself in the tick before by its stable id and mixing its matrix, its bones, its own positions, its colour and the lens. It costs a tick of delay and a copy of the packet a tick. Read on this machine's 100 Hz panel: 60 refreshes a second with a tick and 40 between, none late, and eight refreshes in a row are eight different pictures 0.6 of a tick apart. Found doing it: a window's vsync doesn't pace the loop (600 refreshes a second), so the loop keeps the display's beat itself; and a dynamic buffer lives in one frame's ring, so a frame nobody drew for has to carry them over. Off in the anim lab (a frame there is an exposure) and under a fixed step, a tape or a recording. `REVA_INTERP=1` puts it on anywhere; `REVA_BTWDBG=<folder>` counts and saves.
    **The lens: depth of field, motion blur, anti-aliasing over time** (`dof`, `mblur`, `taa`; `shaders/lens.frag`, `taa.frag`; `lensPasses`). Passes between the scene and the post pass, on the scene's own light. Depth of field gathers from a disc where a point spreads only as far as its own softness, so a sharp subject isn't smeared by the wall behind it; at a softness of 1 it's about a fast portrait lens (the first number was nearly twice that, and everything two units off the focus was mush). Motion blur and the anti-aliasing find where each point was a frame ago from its depth and the two lenses, so it's the lens's own move they follow. `dof` is on at the PC rungs and does nothing until a frame's lens asks; `mblur` is on for film alone and `taa` nowhere, as the plan says: blur on a flat panel isn't for everyone.
    **Film's camera track with roll** (this step's line). The set's timeline has a fourth format, TRK4: a lens row (where it is, what it's aimed at, how wide, how far rolled) and a post row, read between the file's frames so a move written at 30 a second is smooth at 60, with a jump of the lens taken as a cut. The lens can roll anywhere now: `cam=...,fov,roll` and `camroll=` on a ctl line, `camroll=` on a scene's line, `lens roll=` in a set, `E->lensLook` for a game's cutscene.
    **Post per frame.** The post row, and the same things as standing settings (a ctl line, a set's `film` and `lens` lines, a scene line's `focus= shutter= sepia= grain=`): exposure, haze and grade for the frame, the lens's focus and shutter, sepia, grain, a white flash, a film burn eating in from the frame's edge, and the gate's weave. `trackt=<seconds>|play|off` holds or runs a set's timeline in the lab with no scene playing.
    **HDR on the glass** (`hdrout`). Only where the display says it takes HDR10. The picture below white is exactly the one every display gets, at 200 nits; the light each pixel had past white is kept in a picture of its own (`shaders/hdrex.frag`) and the presenter adds it back in the display's primaries and curve, up to a peak (1000 nits, or the setting's own number). This machine's display says yes, and a frame was drawn that way. ⛔ **I can't see what it looked like:** a shot reads the ordinary picture under it. It's still to be looked at by eye.
    **The fair view** (the plan's rule for versus play). A game says the shape its picture is played in (`E->tune->fairAspect`), and on a screen wider than that the world is drawn in a view of that shape through the same lens, with black either side; split screen is laid inside it; the HUD keeps the whole screen. `REVA_FAIR=1.3333` shows it on a game that doesn't say.
    **The test scene** has the film cut (`everything.py --film`: the lens tracks, rolls and whips, with sepia, grain, a flash, a burn, focus and shutter from its post row) and the display's settings one after another (`--display`).
    **Not built:** a body's own motion isn't blurred or followed over time, only the lens's (no per-object velocities); the tube has no dot crawl or rainbowing, no glow round bright things, and its mask is drawn in the panel's pixels, so a 720-line window shows it coarse; the picture is scaled to the glass plainly when its size isn't the glass's; HDR has no setting for paper white, and its shots are the ordinary picture; an exclusive display mode at a chosen rate isn't offered (the picture's size is its own instead, and the desktop's mode is never touched); the mouse isn't mapped back from the glass to a picture that's a different size (the mark editor's clicks); the lighthouse door and split screen have no lens passes; the Pi's direct road has none of this, as the plan says.

    **The same pixels on every machine**, which is the other half of what it's for. On floats it uses only add, subtract, multiply, divide and square root, which IEEE 754 rounds one way, and never contracted; exponentials and the like are the club's own math, as tables; a triangle's coverage is whole-number arithmetic on positions snapped to a sixteenth of a pixel, with the top-left rule; colours mix as whole numbers; a float that isn't a number never reaches a conversion to a whole one; one thread, and no clock. 29. [x] Online play.
    Built 11-05. The same game on two to four machines, a pad or more each, and a Pi and a PC can share one. ⛔ **It's lockstep with a delay, and it isn't rollback**, which is what Phase 8's line names. The last paragraph says why.
    **What a session is** (`reva_native/club_net.c`, whose first comment has the whole of it). The rules are a function of the dice and of every pad, tick by tick: that's what a tape is, and why one replays on any machine to the same hashes. So machines play one game by agreeing the dice and then handing each other their pads. Nothing of the world is ever sent. A session costs the wire the same whether the game has two bodies or two thousand, about 5 KB a second each way for two players on a good wire and 10 to 16 on a bad one, and nothing of one machine's speed, screen or settings reaches another.
    **Lockstep, with a delay.** What a pad does at tick T is played at tick T + delay on every machine, the presser's own included. A machine runs a tick only when it holds every pad for it, and waits when it doesn't: a slow wire holds the picture for a moment and never changes the game. The delay is chosen once, when the session starts, from the wire as the host measured it (the quickest of several trips to each player), and it doesn't move after: no automatic cuts. Two ticks on one network, four with 25 ms each way, seven or eight with 60 ms each way and 40 of jitter, and never more than fifteen, a quarter of a second.
    **The wire.** UDP, one port, a star: every player talks to the host and the host passes pads on. A packet of pads carries every tick the other end hasn't said it has, so a lost packet costs nothing but the next one's arrival. The few things that must arrive (the start, the saves, who's gone) go one at a time and in order, sent again until answered. Every machine's clock starts at one moment the host names, found on each player's own clock from the quickest trip, so the machines tick side by side and nobody spends the game waiting on one that began a little late.
    **A session is a whole run, from tick 0** (`engine/net.inc`). `REVA_NET=host[:port[:pads]]` or `join:address[:port]`; or, from a game's own menu, `E->netHost` and `E->netJoin`, which start the engine again in a session the way the start menu's MAIN MENU always has. Four moments. The players gather on a screen of the engine's own, once the game's known and before anything of it is loaded, and the host's dice become everyone's. Everything loads. Each machine says what it loaded (every pack and set by its name, length and bytes, added up) and where its own players have their buttons; the host holds that against its own, and says go. And from then on each tick's pads come in over the globals and `g_padRaw` exactly where a tape's would, so nothing downstream knows a session from a tape.
    **A game's rules see nothing new.** `E->pads` is the session's pads on every machine, as four pads on one machine would be. `E->netHere(player)` says which are this machine's, for what's drawn: whose lens, whose bat is lit. `netState`, `netSeats`, `netLag` and `netWhy` are for the picture too, and `netHost`, `netJoin` and `netLeave` are all a tick may call. `games/rally` is the place to start: bats and a ball for one to four, with no files at all, and a tick that never asks whether it's online.
    **Kept the same by checking.** Every twentieth tick's hash of the rules crosses the wire and is held against the other machines'. Two that part are told the tick at once; the one that parted is out and the others play on. Before the start, a machine whose files aren't the host's is told so and left out.
    **A session is an ordinary tape.** `REVA_RECORD` in a session writes the pads of every machine once they're in: four pads, as any tape. Replayed alone with no wire it gives the same hashes, so whatever goes wrong online can be played again offline. A tape now says when pad 1 is unplugged, which only a session can do.
    **A session's saves are the host's** (`club_save.c`). What a game reads from a save differs from one machine to the next and would part them at the first tick. The host's slots are handed to everyone before anything is loaded and are read from memory while the session lasts; a save made in it goes into every machine's copy, and only the host writes its file, so nobody's own save is written over by someone else's game.
    **Leaving, and being left.** A machine that leaves says the last tick it sent pads for, and the others play up to it before they count it gone, so a game's last ticks are one game too. One that dies without a word is waited for (ten seconds, `REVA_NETTIMEOUT`) and then unplugged from a tick the host names to everyone. A player is there while its pads keep coming, not while it keeps talking; one that never takes the start, or never finishes loading, is left behind. The game goes on for whoever's left, `E->netState` says it's over on a machine that's alone, and its tape still replays.
    **Everything that comes in is a stranger's.** Every length, count, seat, tick and index in a packet is checked before it's used, a packet from an address that isn't the session's is dropped unread, and all a player can put into the game is its own pads, where its own buttons are, and its own word about what it loaded and how its game is going. ⛔ Nothing is secret or signed. A word (`REVA_NETWORD`) keeps a stranger out by accident, not an attacker: it's for a game among people who trust each other, not for a prize.
    **Found by its own check.** `anim_bench/netcheck.py` runs two to four no-display engines on one machine, each with a tape for hands, on a wire made as bad as asked, and holds every machine's hash against the others' tick for tick, and against the host's tape replayed alone. Before it passed it found: a goodbye that raced the other machine's last ticks (they parted on tick 1,200 of 1,200); my sample game's rules reading whether they were online, which no tape carries; a player treating the other players as if it talked to them (three machines never started); the host choosing its delay before one measurement of the wire had come back; a player that joined and then sent anything but pads holding every machine at one tick for ever, and one that never took the start, or never said it had loaded, holding the start for ever; and a machine with no hands sending back what the merge had left in its own pad, so every bat followed pad 1's.
    **Its cases, all the same on this PC:** two machines on a clean wire; on a bad one (60 ms each way, 40 of jitter, a packet in five lost and one in ten sent twice); three machines and four pads, one machine bringing two; two machines drawing at different rates, rungs and reading sizes; the real clock for five seconds at 25 ms each way with 3% lost (a handful of the 300 ticks held on one machine, 2 to 7 from run to run and 17 ms at the longest, and none on the other); one machine made to play a tick with a pad nobody was sent, which both must notice and name (the check that has to be able to fail); a player's machine dying without a word, and the host playing on to the end with its tape still replaying; the host and the player with different saves, where both play the host's and the player's own file is untouched; broken packets thrown at the host all game from a stranger's address (about 1,900, all dropped unread); and a third player that joins properly, plays 200 ticks with nonsense on every side of its pads, then lies about its hash and is put out, while the two real machines never differ.
    **And on other builds, from this PC** (the build container): every case the same on Linux; a PC's build hosting with the Pi's ARM build playing under emulation, on the clean wire, the bad one, three machines, a dead player and the two saves, and the Pi's build hosting a PC's; and every case again on a build with the compiler's memory and undefined-behaviour checkers in it, with no finding in any of its 31 logs. One real window was looked at as well: the game hosting on Vulkan with a second engine joining that has no display, the same hash on both, the host's waiting screen with its address on it, and no tick held in seven seconds. `scenes/everything.py --net OUT.png` is the picture of it: two machines on the engine's own rasterizer with no window, each one's frame at the same three ticks, the same world in both and each machine's own bat the bright one.
    **Ruling 8** (a 59.94 Hz tube and a 60 Hz panel part by a tick every 17 seconds) is answered by the design: the machine that's ahead holds one picture when it gets a tick past the pads it has. Nothing is made up between.
    **Why not rollback.** Rollback plays ahead on a guess at the other players' pads and, when a guess was wrong, puts the world back and runs those ticks again. Three things are against it here. The world isn't in one place to save: the engine's own state is 92 MB of statics, declared on 2,232 lines across `engine/`, besides what's on the heap, and telling the rules' part from the rest is an audit of the whole engine before a byte is saved. Every tick run again costs a tick, and the plan's own rule is that nothing is built for the PC that the Pi can't play: a Pi's field hasn't a second tick in it for a game of any size. And a tick has effects that can't be taken back by copying memory: a sound that's started, a file that's read, a pack that's loaded. What's built instead costs a machine nothing, and is exact. What it gives up is the feel on a long wire: a button is felt two to eight ticks late, where rollback would hide that for the presser. If rollback is wanted, the first step is the engine's state gathered behind one save and one load, and that is a phase of its own.
    **Not built:** rollback; joining a game that's begun, or watching one; a list of games to join, matchmaking, and a relay for machines behind a router that won't open a port (the host's port has to be reachable); IPv6; encryption or signing; the host's place passing to another machine when it leaves (the others each carry on alone); a thread to keep the wire alive while a machine loads for longer than the timeout; pulling a machine's music back onto the session's clock after it's waited (in a session the music clock is the tick's); the engine's own pause menu in a session (it's off: its screens are one machine's); the old doors (a session is a game's); a waiting screen that's more than text. On a machine left alone after a session, its own pad still arrives the delay late until the game calls `E->netLeave`. ⛔ **Every session so far was on this PC, over its own loopback, with the wire's faults made by the engine itself. No two real machines have played, and no real Pi.**

- **Objects a game makes and takes away** (`engine/objects.inc`, 11-03). `E->prop` names a model, `E->spawn` puts one in the world and gives a handle, `E->place` moves it, `E->paint` colours it, `E->despawn` takes it out, and `E->object` says what it is now. 1024 at once, and a handle is never given out twice, so a stale one is safe: calls on it do nothing. They draw the way a set's props do, with shadows and culling, and copies merge into one call. `OBJ_SOLID` makes one stop bodies and rays: by its real triangles on a `climb` set, so it can be stood on, and as a circle on any other set. Moving a solid one along costs next to nothing, because its columns go with it, and it carries whoever's standing on it. `E->bodyNew` and `E->bodyGone` wake and put back bodies from the pool. It's all in `[simhash]`, and a run that never makes one mixes nothing, so no other game's receipt moved. `games/tower` uses all of it: crates you can jump on, beacons that change colour, and a lift. With nobody at the pad, its hero walks the same path to the last digit as before the crates were there. `anim_bench/objcheck.py` is 102 checks through the same table any game gets, and 12 deliberate breaks of the engine each fail it. It also found two older bugs in the walked world, both fixed. A ray further than about (W+H+4) x 0.2 units from a small grid went straight through it, which would have hit streamed cells too. And a body falling beside a wall could then walk through the wall, because anything in its circle let it go anywhere. Now it can walk along what's touching it or out of it and never further in, grid by grid, and a move longer than a cell is walked a cell at a time, because a surface is one cell thick and a tall box is hollow. - **Physics a game can reach** (`engine/objects.inc`, `engine/ragdoll.inc`, queue step 9, 11-04). `OBJ_LOOSE` on anything from `E->spawn`: it falls at real gravity, bounces less each time, slides to a stop in the time friction says, stays put on a slope its grip can hold, rolls if it's `OBJ_ROUND`, and comes to rest. It lands on what's really there, because it uses the walked world's surfaces: a crate lands on a deck, stops at a wall and slides off an edge. A tall thing pushed high up goes over onto its side, and a nudge at its foot leaves it standing. Loose things stack and knock each other along, and knocking the bottom one out brings the stack down. `OBJ_RESTING` starts one asleep where it's put, in the air if you like, until what's under it changes or something hits it. A solid one can be stood on while it's asleep, and a body walking into one that's awake shoves it along. `E->push` and `E->pushAt` move one, `E->feel` sets its bounce and grip, `E->objectOnRay` says what a straight line meets, and `GameExport.objectHit` says what hit what and how hard, once a touch, and a game can take either away inside it. Any body goes limp with `E->bodyLimp`, and -1 is the hero: the ragdoll film uses, on what's really there, from whatever pose it's in, and `E->bodyRise` puts it back on its clips. 16 others at once. `games/tower` uses all of it: a punch sends a crate flying, a crate going fast enough knocks a chaser down, a chaser that's knocked down falls limp and is gone 3 seconds later, and whoever's caught goes down. Loose things are all in `[simhash]`, and a limp body is what's drawn and not the rules: with and without one, `[simhash]` is the same and `[packet]` parts. `anim_bench/physcheck.py` is 134 checks through the same table any game gets, on a `climb` set and on no set, comparing every hit's tick at odd tick patterns and measuring each fall from the ragdoll's own log, and the five deliberate breaks tried each fail it. Each experiment has been looked at on Vulkan too. A game's bodies showed three things wrong in the ragdoll, fixed for them and left alone for film, whose takes were made on the old ones: friction read how deep a joint was after the floor had already put it right, so there was next to none; two rules split a correction evenly between a heavy joint and a light one, which pushes the whole body along, so a body crawled along its own length on the floor at 5 units a second; and a body standing with straight legs kicked its feet half a metre up as it went down. And an old rule banned any body whose drawn hips were more than 4 units from its place on the floor, so a body thrown that far was lost to the pool for good, which was the one way a limp body reached the rules: found by a deliberate break, and a game's limp bodies are exempt now. **Not built:** this is one point with an orientation, not a solver of corners, so a box doesn't rock and a stack doesn't lean before it goes. There are no joints or hinges between objects, and no vehicles. A limp body off screen doesn't fall until it's seen, which is why no rule may wait on `E->bodyLimpState`.
- **What a bigger game needs** (`engine/gameworld.inc`, queue step 16, 11-04).
  - **Changing level.** `E->level` loads another set while the game runs, behind a fade if it's asked for one. What the old level had goes: what the game spawned, the props, and a few ticks on the memory of any pack nothing's using now. `GameExport.levelIn` is where a game puts things in the new one, with the screen dark. Tried by going between two levels 1,682 times as fast as they'd go: the process stayed at 278 MB and geometry at 0.3 MB. **Not built:** the load itself happens between two frames, so it's a cut and not seamless. A game that wants no cut has `cell`.
  - **Finding a way.** `E->path` gives points to walk to in a straight line. On a set that says `climb` the first call on a level makes a map of where a person can stand and step: a point every half a unit on each surface, and each link is the real `E->walk` itself in short steps, so what the map says is what a body will do. After that a search only reads the map, so it's quick at any distance. On the tower it's 35,000 places, made in 257 ms, and the way from the floor to the top deck looked at 9,900 of them in 1.5 ms and came out as 6 points: across the floor, up the ramp, up the stairs. A body walked them with `E->walk` and got there. What's been spawned since the map was made is asked about on the way. If there's no way it gives the way to as near as it could get. On a set without `climb` it's the nav grid actors use. **Not built:** a streaming world, or a walker a lot wider or narrower than a person, has no map and searches the columns live, with a budget. It can't jump a gap or use a lift, and the walker is the game's.
  - **Props on any bone.** `E->attach` puts a model on a bone by its name in that pack or by a plain word (head, hand_l and so on), and it goes with the bone wherever clips, a face or a ragdoll take it. The offset and scale are for a body of ordinary height, so the same crown fits a child. 256 at once, on and off whenever the game says, with nothing added to the pack, and a conversation file can do it with `attach` and `detach`. They're what's drawn, not the rules, and they cast shadows.
  - **A music clock.** `E->musicClock` after `musicPlay`: beats a minute, where the first beat is, beats to a bar. `E->musicBeat` says where it is, and `GameExport.beat` falls on the tick each beat comes round. In a live game it follows the sound itself, because a late frame slows the game by a hair and the sound doesn't stop for it, and a tape keeps what it read, so a replay's the same session. In anything measured it's the tick clock and no sound's involved. At 120 beats with the first at 0.25 s, beat 16 fell at 8.25 s to the tick, on the recording and on its replay. **Not built:** nobody has played to it with the sound on yet.
- **People built while a game runs** (`engine/people.inc`, queue step 15, 11-04). Whether players make their own character is each game's call, and the engine needs the capability and the feature. The people builder was a Python tool, so a game couldn't call it. `E->bodyBuild` is one in plain C, from the same measurements and tables: a body is a stature, how many heads tall it stands (5.5 at five years old, 7 at twelve, 7.5 grown up, and the whole body's proportions follow), how it's built, shoulders, waist, hips, limbs, legs, bust, belly, nose and jaw. It has skin, eyes, three hairstyles and a bob with their colours, and sleeves and shorts, trousers or a skirt. It writes an ordinary pack into memory on the stream's thread and the ordinary loader reads it, so a built body is the same as any other: it stands, walks and runs by itself, takes clips from a bank, is lit and casts shadows, and its face does everything step 14's can, with a jaw, eyes on bones, lids, a smile, brows, a mouth that opens and teeth inside it. The same spec builds the same bytes on any machine, and it's about 2,500 triangles and one small texture. `E->heroWear` puts one on the hero, which nothing could do before. `E->tune->heroSpd` below 0 now means the stick doesn't move her, because a menu needs the stick. `games/people` is the slice, and the place to start a game whose players make their own person: a menu that changes a person live while a street of people dealt from the dice stands behind, none of them made ahead of time. What it writes passes `packdump.py --check`. **Not built:** this isn't film's person: the hair's a shell and flat panels, the face is painted, and hands are mittens with a thumb. There are no separate garments, so clothes are the skin's own colour, with nothing that hangs. A built body only has its three clips of its own, though a bank's work on it. And how it looks is still to be judged by eye.
- **Faces and conversations** (`engine/face.inc`, queue step 14, 11-04). Any body, and the hero, can blink, breathe, say a line, look at something, and take a shape by name. `E->bodySay` plays a sound on the voice bus and its own loudness moves the mouth and the head, and if there are words the shape of them opens and closes the jaw as well. With no sound, the mouth moves on the words alone for as long as they take to read, so a game has talking people before it has a single recording. `E->bodySayData` and `E->bodyMouth` feed a mouth from a game's own data, for a song's lip sync. `E->bodyLook` and `E->bodyLookBody` turn the head and eyes, the eyes first, with a neck's limits. `E->bodyShape` holds any shape. Each body has its own face, even on a pack others are wearing, because its moved positions go in the frame's packet. It's all drawn and not the rules: with a face on the hero, `[simhash]` hashes the pose from before it went on. **A conversation is a text file,** `talk/<name>.talk`, read each time it starts: who says what, the lens, who looks at whom, shapes, a value for a body's animation graph, a beat, wait for a button, a question put to the player with its answers going to labels, an event for the game, and A cuts a line short. Left to itself the lens opens on both of them, goes over a shoulder onto whoever's speaking, and cuts in close every third change, always on one side of the line between them and never through a wall. The words go up on the TV's grid and fit any reading size. When it's over the lens goes back to what the game had. `games/talk` is the slice, and the place to start a game whose people talk, with its bodies, room and voices made by code. A voice is read and its loudness worked out on the stream's thread, and it's let go after a minute with nobody using it. **On Vulkan** this brought the mouth's opening across (a hole cut between the lips, drawn by its own two pipelines, so nothing else's shaders changed by a byte) along with the jaw on a bone and shapes per body. On film's current Reva the mouth opens centred and dark. `E->heroFace` is new too, because a game had no way to turn the hero. ⛔ `v1_r2moves` opens to one side: its lip marks and its teeth don't line up with each other, which is that pack's and not the engine's. **Not built:** a seated body's shot sits too high, because the lens uses how high its eyes are at rest. Split screen doesn't get its own conversation lens. The mouth's shape is how far it's open, not which sound it's making. And nobody has listened to it yet.
- **A long session** (queue step 13, 11-04). The engine can run for as long as anyone leaves it. Bodies of different sizes coming and going used to fill the renderer's list of freed memory in two minutes, then what was freed was lost for good, and the memory grew until the engine exited. Now a freed piece joins the free pieces either side of it, and a buffer that grows gives back what it had. A buffer's or a texture's name comes back when it's deleted, so the renderer's tables stop at about the size the game needs. A place in the set's table comes back too. A game can let go of a model with `E->propDone`: its memory goes, its number still works, and the next spawn reads it again. A model the set was using first stays, and so does one with anything out. And a pack that comes back says nothing about itself the second time, because that's what filled a long session's log. `REVA_MEMSAY=<ticks>` prints a `[mem]` line, so a long session can be read. **Tried:** 16 kinds of body changing on four bodies at 10 changes a game second, run as fast as the machine would go. Before: 50 to 213 MB of geometry in under two minutes, and a 41,000-long name table. After: one block, about 53 MB, 2 free pieces, and the tables flat. **Not built:** a game's own images and sound bank aren't let go, and the cells a level loaded stay until step 16.
- **A game's state is in the receipt** when it gives `stateSize`. A flat game has no hero or bodies, so its `[simhash]` didn't move at all before this.

**Gate:** each kind's replay. An explicit go or no-go on big open worlds, on SD and on SSD. This was the highest risk in the plan, because nothing about streaming had been measured.

**Big open worlds: go.** This Pi boots from a USB stick that reads 28.7 MB/s, slower than most SD cards are specified for, and the fastest run above needs about 2.7 MB/s. So the disk isn't what limits a big world on this hardware: the picture's budget is, as it is everywhere else. ⛔ That's measured on this stick only. Neither SD nor SSD has been measured, because neither is here, and the work goes on with the hardware at hand (11-03). Far detail, bodies that stream and a long session have all been built since (queue steps 12 and 13, above).

**Where it stands (11-03).** Steps 1 to 3 are built on the new renderer, and steps 4 to 7 aren't started. ## Two engines to learn from

Both were put forward on 11-02. Neither can be the base: raylib is OpenGL only, and its FAQ says there are "no plans to support any other graphics APIs", and Wicked assumes bindless textures with no fallback, which the Pi's Vulkan driver doesn't have. Both licenses let us copy code as long as its notice stays (raylib zlib, Wicked MIT).

- **[raylib](https://github.com/raysan5/raylib)** (plain C99, and its Pi road is DRM/KMS like ours) is a parts bin for the gaps. `raudio` for streamed music, which builds standalone on miniaudio (Phase 6). `raygui` for UI and settings, one header with a standalone mode (Phases 4 and 6). Its evdev pad reading for four players (Phase 6). `raylib.h` and its 220+ examples are a model for `engine.h` and the public samples (Phases 3 and 8).
- **[Wicked Engine](https://wickedengine.net/)** (C++17) is the reference for Phase 7: its features match that list closely, each readable in one codebase. It targets Vulkan 1.3 too, and its one device interface over three backends is a model for our thin layer. Read its job system, GUI, loading screen, in-game console and Jolt physics before building ours in Phase 6. Its VRM import is a possible route to new bodies from VRoid Studio.

## What we said no to

Automatic quality cuts of any kind. A script language. Overclocking. AI inside the games. Tuning to one TV. A big-bang rewrite. An ECS library, fibers, and SDL3 GPU, sokol, bgfx or the Vulkan Memory Allocator in place of our own thin layer. Virgo as the engine's renderer. Reading files on the frame thread in a shipped game. PAL modes on the NTSC test set.

## The rulings

Each has a working default, so nothing is blocked except where it says so. Gone over on 11-03.

1. **HDMI and composite at once: parked.** There is only the one connection for now, so it isn't important yet, and how it was done on the Pi before isn't on record. Build for one connection and SSH for now. The two-screen dev setup comes back when a second screen is in play, and the Pi docs and the only config measured say the two are exclusive, so it needs finding again then.
2. **"Same bodies".** Ruled 11-03: same skeleton, clips, collision and count on every machine, with mesh detail as a visual setting, so the Pi's Kaeli has fewer triangles than the PC's. A PC may show extra background people as a visual setting, as long as they never affect play.
3. **What zero means.** A test can only bound a rate: 1 clean minute shows at most one late frame per 20 s at 95% confidence, and it speaks only for that minute: the horde's first 5.7 minutes had 5 late and its full 10 had 1,517, so a number says which minute it covers. Ruled 11-02: no 3-hour soak, and 1 minute in place of 10. Budgets and margin carry the rest.
4. **Mode switches.** Ruled 11-03: a switch doesn't count as a dropped frame. Behind a cut or fade only, and not counted as late.
5. **50 Hz TVs** can't physically show 60 images a second. With no 50 Hz PAL TV to test on, it's a to-do for much later (11-03). The to-do: restate the rule as one new image per field, offer PAL-60 first, and find a PAL volunteer.
6. **The rule during development.** Developing solely on the Pi will be awkward; the plan has it right, and it's a to-do for later (11-03). It applies in play mode, with the agent and compiler stopped. A Pi can't hold it while compiling: memory misses by up to 0.27 GB, and a compile has already cost a flip.
7. **"Any Pi 4".** Ruled for now, 11-02: this model is the one in use. We prove on this model at stock speed, and older 1.5 GHz boards wait until shipping comes up. Still the default: state the cooling on the box, and exclude keyboard models from composite because they have no composite output.
8. **Online between different refresh rates.** A 480i Pi and a 60 Hz peer differ by one tick every 17 s, so something has to repeat or be synthesized. Default: decide in Phase 8. **Decided by building it, 11-05 (queue step 29):** something repeats. The machine that's ahead holds one picture when it gets a tick past the pads it has, and nothing is synthesized.
9. **`lighting_rung.md`'s order.** Ruled 11-03: add the lighting, since more capability and functionality are needed there. Phase 7 replaces its engine half, with no waiting on the Pi. Its game-feel work is game work and can continue in the games at any time.
10. **Does the dance floor stay in the engine?** Ruled 11-03: the dance floor is the free-model asset showcase, and it stays in the engine. The crowd's dancing, the beat clock and the venue are woven through the crowd loop. The case for moving them behind `engine.h` may be right, so it stays for now, and that move is left open.
